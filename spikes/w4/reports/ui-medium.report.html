On the Projects page, show how many projects the signed-in user has in …

Verdict PASS REVIEW PASS

Summary

The ticket asked for the signed-in user's project count in the Projects heading and in the top-nav Projects link, and for an empty state with a link to /projects/new when the user has no projects. This change does all three, in server.js only. All five requirements pass against this HEAD (verdict PASS, medium risk). Alice, with one project, sees "Projects (1)" and "Projects · 1". bob-admin, with none, sees "No projects yet" and the link to /projects/new. The proofs were run by the engine. The nav count is proven on /settings only.

What changed

  • Count: server.js:205 counts the signed-in user's projects on each signed-in request.
  • Heading (R1): the Projects page h1 carries data-testid=projects-heading and shows the count. Alice sees "Projects (1)": e30.
  • Nav link (R2, R3): the Projects link at server.js:90 carries data-testid=nav-projects and shows "Projects · N". On /settings alice sees "Projects · 1": e33.
  • Empty state (R4): server.js:266-269 shows "No projects yet" with data-testid=projects-empty. bob-admin sees it on /projects: e36.
  • Create link (R5): the link "Create your first project" has data-testid=projects-empty-create. Its text is checked in e39 and its href is /projects/new in e40.
  • Screenshots: the empty Projects page is at e43. The populated page, with the "Onboarding" project, is at e46.

What a human must check

  • R3 ("every page") is proven on one page only. C2 checks the nav count on /settings for alice. Nothing in the evidence shows the nav count on other signed-in pages. The nav link is built at server.js:90. Read that code and confirm every signed-in page gets it.
  • The count query at server.js:205 runs on every signed-in request, before routing. That includes /api/me, 404s and the logout POST. There is no index on projects(owner_id) (db/001_schema.sql:17-25), so each count is a sequential scan. The reviewer raised this as a note. Decide whether to add an index in a later migration, or compute the count only when a page renders the nav. This change adds no migration.
  • With zero projects the heading reads "Projects (0)" above "No projects yet" (server.js:269). The ticket does not cover the zero case. The spec's assumptions accept "(0)". Decide whether to drop the count when it is zero.

Review

Lenses: code, ux, ui. 4 note(s). A finding blocks only when it is demonstrable (a line at HEAD, a requirement, stamped evidence) and not low confidence.

idlensconfidencewherefinding
code-1-1codenotehighserver.js:205 · R3per-request count query on every signed-in request has no index on projects.owner_id
Line 205 runs `SELECT count(*)::int FROM projects WHERE owner_id = $1` for every signed-in request, before route dispatch, so it also runs for /api/me, 404s and the logout POST. db/001_schema.sql:17-25 defines `projects` with no index on `owner_id` (only the PK and the UNIQUE on `slug`), so each count is a sequential scan. The existing list query at server.js:264 scans the same way, and the fixture table is tiny, so nothing shows it is slow. Worth a `CREATE INDEX` on `projects(owner_id)` in a later migration, or computing the count only when `page()` renders a nav.
ux-1-1uxnotehighserver.js:269 · R4Empty-state heading reads "Projects (0)" above "No projects yet"
A user with no projects sees the heading "Projects (0)" and then "No projects yet". The ticket is silent on the zero case, and the spec's assumptions accept "Projects (0)", so this is consistent. It is slightly redundant copy, and a person may read "(0)" as a count they are meant to act on. Consider dropping the count when it is zero.
ux-1-2ux, uinotemediumserver.js:90 · R2 · e46 e43Nav count is rendered inside the link text, so assistive tech reads it as part of the name
The link reads "Projects · 1" to screen readers, which matches the ticket's wording. A visually hidden label such as "1 project" would be clearer for non-visual users. This is a taste call, not a defect.
ui-1-2uinotemediumserver.js:266 · R5 · e43Empty-state link uses the default link colour, not the nav link colour
"Create your first project" is rendered in the browser's default underlined link blue, while the nav links use the app's blue. The populated list's project link (e46, "Onboarding") uses the same default style, so this matches the existing in-content link pattern and is not a new inconsistency.
