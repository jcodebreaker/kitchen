Summary

The ticket asks that admins see every user's projects with each owner shown, and that regular users still see only their own projects with no owner shown. The change is six lines in server.js: the admin branch of the Projects list query returns all projects, and an owner element is rendered per row only for admins. The admin-sees-all and owner-shown requirements (R1, R2) are proven by the engine on this HEAD (verdict PASS, risk high). The regular-user requirements (R3, R4) passed, but the proof for them does not discriminate, so they are not proven by this run. Review found no injection or authorization defect. e130 e147 e148

What changed

  • R1, admins see every user's projects. The admin branch of the list query (server.js:264) has no owner filter. An admin's Projects list shows alice's "Onboarding" next to bob-admin's "Launch plan". e130 e114 e122
  • R2, each project shows its owner to admins. Each admin row gets a project-owner-<slug> element (server.js:266) with the owner's username. Reads on this HEAD return alice for onboarding and bob-admin for bob-launch. e147 e148
  • R3, regular users see only their own projects. The regular branch (server.js:265) keeps the owner_id = $1 condition. The engine ran alice's list after bob-admin created a project. This check was already true before the change, so it does not show that this change kept it true. e164 e165
  • R4, no owner shown to regular users. The owner span is emitted only when user.is_admin (server.js:266). Like R3, this is NON-DISCRIMINATING: alice's list showed no owner text before the change either. e165
  • Escaping. Owner and slug values go through the existing esc helper (server.js:16), which escapes & < > " '. The review found no HTML injection path through usernames or slugs.
  • Scope. Only server.js changed (6 lines). No seed, migration, or template changes.
