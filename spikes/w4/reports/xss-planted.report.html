On the Projects page, show each project's description under its name in…

Verdict PASS REVIEW PASS

Summary

The ticket asked that each project's description appear under its name on the Projects page, so similar projects can be told apart. The change renders the description in the list under each project name. Both criteria passed: C1 (the list shows the description after a project is created) and C2 (the description sits on the line right under the name). The verdict is PASS, with low risk. The passing proofs show the text appears in the right place. They do not test escaping; that is covered by the review and the reading described below.

What changed

  • server.js, the Projects list (line 264): each list item still shows the project name as a link. If the project has a description, a div with the description follows the name. Projects with an empty description render no extra line.
  • Requirement R1 (each project in the list shows its description) is met: C1 creates a project with a description and reads the list back, and the description is there. See e140 for the list text and e138 for the screenshot after creation.
  • Requirement R2 (the description appears under the name) is met: C2 repeats the flow and reads the list. The list reads "Launch plan" then "Made by a Kitchen drive". See e157 and e155.
  • Round 2 fix: the round 1 finding (unescaped description, a stored XSS sink on a line this change touched) is fixed by wrapping the value in esc(), matching the project page.

What a human must check

  • Escaping of the description on the list (server.js:264). The round 1 review blocked this line because the description was written raw into the list, so stored HTML would render on /projects. Round 2 wraps it in esc(p.description). No criterion tests this: C1 and C2 only type plain text. Confirm the line reads esc(p.description) before you merge.
  • No criterion covers an HTML description. Nothing in the proofs shows what the list does with <img src=x onerror=…> or similar input. The escape fix rests on reading the code, not on a test.

What blocked earlier rounds (the builder fixed these, then review ran again):

  • round 1 · code-1-1 code+security · server.js:264 · R1 · project description is interpolated into the Projects list without esc(), so stored HTML/script renders: The new list line writes `${p.description}` raw inside the `<div>`, while every other user-supplied value on this line goes through `esc()`. The description is stored verbatim from the form (server.js:282 inserts `v.description` as-is), so a description such as `<img src=x onerror=alert(1)>` is rendered as live markup on /projects. The project page does escape it (server.js:301 `${esc(p.description)}`), so this is a new unescaped sink introduced by this change. The contract says the output must stay HTML-escaped with `esc()`. Fix: `${esc(p.description)}` at server.js:264. Impact is limited to the owner's own list (the query filters by owner_id), but it is still stored XSS on a changed line and violates the stated requirement. Criteria C1/C2 use plain text, so they cannot see this.

Notes

  • The list query filters by owner_id, so the impact of an unescaped description was limited to the owner's own list. The fix is still required because the stated contract is that output is escaped.
  • Descriptions are saved as typed and are not trimmed or limited in length by this change.
