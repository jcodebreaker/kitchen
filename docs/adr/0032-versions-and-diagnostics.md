# Versions, diagnostics and what was checked

**Status.** Accepted, 2026-11-24, by the user (order agreed on a call). Builds on ADR 0019 (one dashboard), 0025 (checks show progress) and 0029 (trust what a run reports).

## Why

1. **Version boundaries are easy to miss.** A running `kitchen dashboard` keeps serving the code it started with: `dashboard.html` is read once, and `dist/` is loaded once. After Kitchen is rebuilt or updated, the page and the data still come from the old build, and nothing says so. The person has to know to restart it, and how. A Report doesn't say what it tested either: which commit of the branch, on which tip of the target, with which Kitchen, tool and models.
2. **Diagnostics are noisy.** When a step fails (the checks, the app, a lane refused three times, a merge), the card and the panel show Kitchen's raw reason (`the build lane failed 3 times: the checks failed: test (exit 1); the log is .kitchen/jobs/…/checks.log`). The useful line is in the log, often not its last line, and what to do next isn't said at all.
3. **Coverage depends on local configuration, and it is invisible.** Whether a Report's green means much depends on which `kitchen.yaml` checks exist, which are switched off, and whether the verify map has a recipe for what the change touched. A repo with Python and no Python checks reads the same as one with them.

## Decision

1. **The dashboard knows when it is stale, and says how to restart.**
   - At start the server records its build: a hash of the contents of the code it runs (`dist/`, or `src/` when Kitchen runs from source), `dashboard.html` and `package.json`. At most every 5 s it looks at those files' sizes and mtimes; once they moved and look the same twice in a row (the rebuild finished writing), it hashes the contents again, so a rebuild that writes the same files is no change and a half-written one is never judged. Nothing latches: a build put back reads as current again.
   - `/data.json` carries `kitchenStale: true` once the build on disk differs, and the restart command. The page shows one quiet banner above the list: "Kitchen was updated · restart the dashboard to use it" with the command and a copy button.
   - `kitchen dashboard --restart` (new) stops the Kitchen dashboard on the port (its pid and KITCHEN_HOME are in `/kitchen.json`) and starts the new build there, detached (log: `<its KITCHEN_HOME>/dashboard.log`), in the same mode, with the same KITCHEN_HOME and node flags: shared, serving the list as it is (`--list-only`: no repo is added, wherever `--restart` runs), or `--private` for the repo it served. Before the old one is stopped, the new build must pass a hidden `kitchen dashboard --check` (its dashboard modules load, a server builds without listening, the page is there), and the pid `/kitchen.json` gives must be the process listening on the port (`lsof`) with a Kitchen CLI's `dashboard` as its command; the home and repo it reports must be folders. `--private` asked of a running shared dashboard (or the reverse) says the running one's mode is kept. The open tab sees a new launch and reloads (ADR 0019's reconnect). Nothing on the port: it starts one, detached (shared unless `--private`). With `--restart`, `--port` names the port only; it doesn't imply `--private`.
2. **What was tested is recorded at QA and shown once per place.**
   - When a job's QA lane starts, the job records `tested`: the branch head and the target's tip (for a check, the tip it drives), the time, how many uncommitted paths the person's checkout had (left out: lanes work on committed code in their own checkouts), Kitchen's version, and the tool with its version when `kitchen run`'s preflight saw it (`claude 2.1.400`). An in-session run's tool version is unknown and not guessed.
   - The Report's "What was checked" section says it, with each lane's model from the job's agent runs. The panel's Checks tab says it under the criteria, with Kitchen's and the tool's versions only (the lanes' models are on the Activity segments). A job without `tested` has no versions line.
3. **One helper says what failed.** `diagnose(kind, log)` (`src/engine/diagnose.ts`) returns `{ what, line, next }`:
   - `what`: the operation in words ("Checks failed: test", "QA couldn't test C2" (ADR 0029's NOT_RUN after its retry), "Kitchen refused the Build agent's work 3 times", "Merge into staging failed", "Proposals failed" (ADR 0029 §6; Kitchen proposes them again)).
   - `line`: the useful line. In a log with `$ cmd` headers, only the last command's section (the first failure stops the checks). Lines that say something passed (`✓ x`, go's `ok pkg`, pytest's dots) and Kitchen's own markers are skipped; a failure in so many words (`FAIL`, `×`, `Error:`, `error TS…`, pytest's `E `) comes first, then any line matching `error|failed|cannot|ENOENT|exit`, else the last line.
   - `next`: the recovery the dashboard really offers for that state: Reply sends a needs-human job back to the lane it failed in (checks, a refused lane: Build or that lane); after QA couldn't test it, "Fix the environment, then Reply: QA runs again (or kitchen resume <n>)"; a merge that keeps failing escalated from review or the merge check, so its Reply carries `to: "build"`, which the server takes only for that diagnosis; Ask for changes sends a Ready job back to Build.
   - `failureOf(repo, job)` picks the kind and the log from what Kitchen wrote (the reason, `checks.log`, `merge.txt`, `app.log`) for a job that needs you because a step failed. The card shows the three lines in place of the raw reason; the panel shows them once, in its ask box, with the raw output one click away (a closed `<details>`; the failing segment adds nothing); the Report shows them first under "What you must check", its header names the stage only, and a why the criteria rows already give isn't repeated.
4. **The Report says what was checked.** A "What was checked" section replaces the bare "Checks" list:
   - the commit tested, the versions (§2);
   - each `kitchen.yaml` check: passed, failed, not run (after a failure; "not in this run (added since)" when everything that ran passed), or off (`enabled: false`, new on a check: "python-tests: off in kitchen.yaml"). A `when: merge` check reads the round's trial merge: failed (merge.txt names it), passed (merged, a PR opened on it, its features waiting or driven), or pending;
   - languages the job's tree has (read from its branch through git, never the person's checkout) that no check covers ("python checks: none in kitchen.yaml"), from the same detection `kitchen init` uses. A Makefile is an entry point, not a language. When some check runs something Kitchen can't read (a script, `make`, `just`, `docker compose run`), the line is muted "can't tell", not red;
   - the verify map: touched features with a recipe (QA drives them), touched features with none ("no recipe: notifications: not driven", or muted "looked at only, not driven step by step" when a merge check looked at it; the merge-check table then drops a note that says the same), and changed files no feature's `Code:` covers.
   A job filed before this ADR has no `tested`; its Report and panel leave that line out and show the rest.

5. **One place for the message hint.** The Running group's header no longer says "Your message reaches the job's next agent": the message box under each running job says where a message goes ("Goes to its next lane"), and that is its one place.

## Not chosen

- **Restarting the dashboard by itself when the build changes:** a rebuild mid-edit would drop the person's open panel and drafts at a moment they didn't choose. The banner says it; the person picks the moment.
- **A file watcher on `dist/`:** a stat of the stamp on the poll the page already makes is enough, and needs no extra process.
- **Classifying failures by asking an agent:** the failure kinds are Kitchen's own reasons, with known words; a regex over them is exact and costs nothing.
- **Asking the tool for its version at every QA start:** it is a process spawn per lane; `kitchen run`'s preflight already runs `--version` once.
