# The project setup contract: scenarios, whoami, doctor, tooling

**Status.** Accepted, 2026-11-24, by the user (order agreed on a call). Builds on ADR 0016 (`app:`, QA evidence), 0025 (a run checks its tools first), 0028 (check tickets and their findings), 0029 (BLOCKED, the run preflight). Superseded in part by ADR 0036 (no second look, so §4's "never gets a second look" no longer applies).

## Why

1. **Test data skips the action under test.** The seed is one fixed state. A criterion like "a member accepts an offer" or "an expired invitation is refused" needs a record *just before* that action, and the seed often has it already past it (the offer accepted, the invitation long expired). QA then hand-seeds through whatever it finds (a SQL shell, a JSON file, an admin page). That is slow and different every round, and sometimes it does the very thing under test.
2. **Identity and eligibility are unclear.** Many criteria depend on who is acting: a role, a plan, an owner. QA guesses which header or login gives what, and a FAIL can be "wrong user", not "wrong code". Nothing in the evidence says who QA was.
3. **Fresh state is hard to trust.** `app.reset`, `app.start`, the health check and `app.stop` are written once by `kitchen init` and never tried until the first QA lane. A reset that fails, or a stop that leaves a container running, shows up mid-run, after money is spent. Nobody can tell whether a reset is per job (compose project per job, ADR 0021) or shared by every job at once. Tools a project needs (a browser, a proxy, a Python venv) are found missing the same way.
4. **A check can't proceed when test tooling is missing.** A check ticket (ADR 0028) asks QA to verify something the project has no way to run: no test runner, no fixture loader. Today QA can only say BLOCKED (and the check is retried) or report a "problem" that is really a missing tool.

## Decision

1. **Scenarios.** kitchen.yaml `app.scenarios: { <name>: <command> }`. Each command prepares one specific state on the running app, stopping just before the action a criterion tests, and prints JSON naming what it made: record ids and the identity to log in as (`{ "offer": 41, "as": "ana" }`).
   - `kitchen qa scenario <job> <name>` runs it from the job's worktree against the job's app (`$BASE_URL`, `$PORT`, `$COMPOSE_PROJECT_NAME`, `$KITCHEN_JOB`). It saves the JSON as `scenario-<name>.json` in the QA folder, the evidence a row cites, and its output in `scenario-<name>.log`. Output that isn't JSON fails the command, and the log stays.
   - The QA brief lists the scenarios. The QA role says: prefer a scenario over hand-seeding; after it, read the state back through the app (a GET, the page) before acting, because the JSON is what the scenario says it made and the app is what is true.
   - The link to intake: a criterion's `· given:` precondition (ADR 0031 §4) may name a scenario (`- C2 (http): ana accepts her offer · given: scenario offer-pending`). QA runs that scenario, reads the state back through the app and cites both in the row's `given` evidence. A criterion with no `given`, or one that names no scenario, leaves QA to pick one from the list.
2. **whoami.** Optional `app.whoami`: a command, or a path or URL on the app, that returns the effective identity and its key attributes (`{ "user": "ana", "role": "member", "plan": "basic" }`). `kitchen qa whoami <job> [--header 'K: v']… [--as <who>] [--name n]` saves `{ "identity": <the answer>, "asked": { via, as, headers } }` as `whoami.json` (or `whoami-<as or name>.json`: always `whoami-…`, so it never overwrites `verdict.json`; `.txt` when the answer isn't JSON) in the QA folder. A path is a GET with the headers; it refuses `--as` without a `--header`, since it would be asked as nobody and saved as someone. A command gets `$BASE_URL` and `$KITCHEN_AS`. `--header` is for a path whoami only (a command gets who to be in `$KITCHEN_AS`); the `--as` file suffix keeps letters, digits, `.`, `_`, `-` and turns anything else into `_` (`ana@example.com` → `whoami-ana_example.com.json`). Secret request header values (`authorization`, `cookie`, `x-api-key`, any `*token*`) are masked to their first 4 characters in every saved file and log, `kitchen qa http` request lines too. Response headers are kept as sent, every `Set-Cookie` among them: it is the local test app's session, and QA needs it (and a CSRF token) to go on. The QA role captures it before any criterion whose result depends on who acts, and cites it in that row.
3. **`kitchen doctor`: the app's steps only when asked.** Kitchen can't tell from a command whether it touches the person's own data: a compose app may run its migrations on the host's `DATABASE_URL`, and `app.start` itself may migrate or seed with the inherited environment. So it doesn't guess.
   - **`kitchen doctor`** runs `requires`, the browser, and a static report of what kitchen.yaml says about the app. Every app row reads "not tried (kitchen doctor --app tries prepare/start/health/stop)".
   - **`kitchen doctor --app`** first says "this starts your app with your shell's environment: if it migrates or seeds on start, it touches whatever DATABASE_URL/env points at". Then, on a throwaway checkout of `HEAD` (under `.kitchen/doctor/`, removed after), it runs the prepare step QA runs (`checks_install`/`checks_prepare`, never the person's `node_modules`), start, health and stop once. Each is reported **ok**, **missing**, **failing** or **not tried**, with the fix.
   - **`kitchen doctor --reset`** is `--app` plus `app.reset`, after "this runs app.reset: it may wipe the data your local app uses".
   - **A fixed port that already answers is left alone** (`app.port`, or a port in `app.url`). Before starting, Kitchen asks the health URL and tries TCP connects on 127.0.0.1 and ::1, since a server on `::` or 0.0.0.0 answers one of them. If anything answers: `start  not tried  port 3000 is in use (another job's app or yours)`, and nothing is reset, started or stopped there. QA's `kitchen qa up` and the merge gate refuse the same way, and stop nothing either:
     - `kitchen qa up` writes the line to `app.log`; QA says BLOCKED citing it.
     - A job whose own detached stack (`docker compose up -d`) still answers is simply up: `kitchen qa up` reuses it rather than refusing itself.
     - A merge check whose app hits the port is not the change's fault. The job is held at Ready ("merge check waits: port 3000 is in use (another job's app or yours)"). `kitchen job next` tries it again once the port is free, spending no round and no catch-up.
   - Examples: `health failing  not healthy at http://127.0.0.1:PORT/health within 60s` and `stop   failing  still answers after stop: add app.stop (e.g. docker compose down)`.
   - **Cleanup.** The app's state goes to `.kitchen/doctor/app.json` as soon as it is spawned, with the start times of the doctor and the app. Ctrl-C or SIGTERM, at any step (a `requires` check, the prepare, the reset, the app), ends the command running then (its process group) and the app. Once a reset has run, cleanup also runs the stop command (`app.stop`, or a compose app's `down`), after a reset that failed or was interrupted too. Then the checkout is removed. After a crash, the next doctor or the orchestrator's sweep (ADR 0029 §5) stops what is left, but only when the app's pid is still that process. One doctor runs at a time per repo; a second says "a kitchen doctor is already running (pid N)" at once.

   **`kitchen init` never resets, starts or stops the app.** It runs `requires` and prints the static report ("set" rows), then "run kitchen doctor --app to try prepare/start/health/stop (and --reset when it's safe)". An error there is said, never fatal.

   kitchen.yaml `requires: [{ name, check, fix }]` declares what the project needs on the machine (`{ name: venv, check: "test -x .venv/bin/python", fix: "python3 -m venv .venv && .venv/bin/pip install -r requirements.txt" }`). `kitchen doctor` runs each check from the repo and prints ok or failing with its fix. `kitchen run`'s preflight (ADR 0025, 0029) runs them too and refuses with the first failing one's fix line: `kitchen run: venv isn't ready: python3 -m venv .venv && …. Nothing started.` Like the browser (ADR 0029 §4), the session itself runs them, never a detaching parent (a wake), so a wake is never blocked and the refusal lands in the run's log. `kitchen doctor` exits 1 when anything is failing.
4. **Missing tooling becomes a build ticket, and the check comes back.** A check's QA may return a finding with `kind: "tooling"`: its `title` names the tooling ("a test runner"), `seen` says what the check needed it for, and it cites evidence (no repro needed). It must name its `criterion` (or several, `criteria: ["C1", "C2"]`), and each row must be NOT_RUN (ADR 0029 §2): missing tooling is exactly why it couldn't run. A tooling finding on a FAIL or PASS row is refused; a FAIL needs a real finding and stays a problem. A tooling finding covers only the rows it names, and tooling findings with the same title in one check are one proposal: it takes every one of their inbox items, so each finding links to it by its key (ADR 0031 §5). A tooling finding needs no `expected` or `cause` and never gets a second look (ADR 0031 §5), even on a high-risk check: it claims nothing in the app is broken, only that a tool is missing. Other NOT_RUN rows keep ADR 0029's path: QA runs again on them (fresh seed), then a person. A real FAIL (a FAIL row, with its own finding) keeps ADR 0029's rule: the check is done and everything is proposed, problems and tooling. Without one, the check waits for tooling only when every NOT_RUN row is covered; otherwise those rows are retried first, and QA names the tooling again in that round. A tooling proposal that fails to save is retried like any other (ADR 0029 §6), and the check waits by its id once it exists. Kitchen proposes it in the inbox as a chore, "Add <tooling> so <check> can run", linked to the check job like any finding (ADR 0028 §4). The check is done with "Waiting for tooling: p3". The proposal carries the check's target, so its job builds from and merges into the branch the check runs on. When every tooling proposal it made has been run and its job has merged **into the check's target**, `kitchen job next` files the check again (same text, same target, a check) and says so in its output. The two are linked both ways: the old check says "Tooling merged: filed again as 014" and its Report is written again; the new one records where it came from (`refiledFrom`, written with the new job, so a crash between the two never files it twice). A check whose filing fails keeps the error on its card and Report and is tried again on the next wave, without stopping the others. If the check filed again still finds the tooling missing, its proposal says so ("Tried before: check 002 proposed p1, which merged…"). A tooling proposal set aside or held keeps the check waiting; nothing is filed without a merge. The Report lists missing tooling apart from the problems found.

## Not chosen

- **Scenarios as SQL or fixture files Kitchen loads:** that ties Kitchen to a database. A command can use the app's own API, a script, or a seed tool.
- **Kitchen logging QA in as the scenario's identity:** apps differ (headers, cookies, tokens). The scenario names the identity and QA uses it the way the verify map says.
- **Doctor starting the app in the person's checkout:** a reset there would wipe their local data. The throwaway checkout is what a job sees.
- **Running every reset in doctor and init:** a throwaway checkout doesn't make a shared database throwaway. A reset runs only on `--reset`.
- **Guessing isolation from command text** (a compose start, a reset "in the project"): it was wrong in common layouts (`docker compose up -d db; npx prisma migrate reset` on the host's DATABASE_URL, `-p myapp`, an inline COMPOSE_PROJECT_NAME), and the guess decided whether a person's data was wiped. The person decides, with `--app` and `--reset`.
- **Binding the port to see whether it is free:** on macOS a server on `::` or 0.0.0.0 doesn't stop a bind on 127.0.0.1, and doctor then ran app.stop against the person's own server. Kitchen asks the port instead.
- **Borrowing the person's `node_modules` (a symlink):** tools write into it (generated clients, bundler caches), and it skips the install QA really runs.
- **Filing the tooling ticket straight into the queue:** it spends money before anyone looked (ADR 0028). The person runs the proposal.
- **Re-filing the check as soon as the tooling job is accepted:** the tooling isn't on the target until it merges.

## Later

Agent and forge adapter contracts. The agent tool (Claude Code, Codex) and the forge (local, GitHub) are switched by `if`s in a few places today. A written contract for each, the way this ADR writes the project's, would let a new one be added and checked by `kitchen doctor` without touching the lanes. Not now: two of each don't justify the layer yet.
