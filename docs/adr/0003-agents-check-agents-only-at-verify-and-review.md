# Agents check other agents only at Verify and Review

A separate verifier, which never wrote the code, drives every acceptance criterion through the Toolkit, and its Verdict decides whether a job moves on; the builder's own evidence is a hint, never the proof. Apart from Verify and Review, no agent checks another agent's work: correctness of everything else is guaranteed by structure or by scripts (the stage machine refuses illegal moves, spec-lint runs before building, the gate runs main's checks, and the report can only cite evidence by id, which the CLI resolves to real files or refuses). We chose this because research shows models don't reliably catch their own mistakes, while stacking agent-on-agent checks at every step adds cost and noise without proof that it helps.

**The spec is checked against the ticket by structure, not by an agent** (W3a review round 2). A spec can be internally sound and still prove the wrong thing: the round-1 admin run dropped "with no owner shown" from the ticket and every check passed. Instead of a second agent reviewing the spec, intake writes the ticket's requirements as a numbered list (`## Requirements`, R1…Rn, each a quote or faithful paraphrase, the ones that say what must not happen marked `(negative)`, a rescoped one marked `(out of scope)` with why), and every criterion names what it proves (`covers: R2, R3`). spec-lint refuses a contract where a criterion covers nothing or an unknown R, a requirement in scope is covered by no criterion, or a negative requirement is covered by no criterion whose mechanical expect asserts an absence. That coverage rule is the structural spec check; whether a criterion's proof really shows its requirement is still Verify's (it must fail a wrong build) and Review's job. Intake's list is the one place an agent's reading of the ticket is trusted without a check, and it is short, quoted, and shown to the reviewer.

**Review decides nothing by itself either** (W4). A review lens writes findings; the engine decides which block (`src/checks/findings.ts`). A finding blocks only when it is demonstrable, which the engine checks against its own records: it names a line that exists at HEAD, a requirement of intake's list that is in scope, or evidence ids that are in the verified manifest, and every anchor it names holds. `confidence: low` never blocks. Everything else is a note, shown to the person who merges and kept out of the builder's next round. Findings from different lenses about the same line (or requirement) are merged, and every lens's counts (claimed blocking, blocked, kept as a note because low confidence or not demonstrable, merged) go to the ledger, with `kitchen dismiss` dismissals per lens, so a lens that keeps crying wolf shows up (W5's retro mutes it). This follows what made production review bots tolerable (confidence filters, de-duplication, muting what people dismiss) without a second agent judging the first. The UX and UI lenses still never drive the app: they ask for views, which the engine runs and stamps like any proof.
