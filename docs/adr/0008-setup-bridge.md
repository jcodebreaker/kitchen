# The setup bridge runs agent-written bin/dev, confined by an OS sandbox

**Decision.** `kitchen init`'s setup role gets its own engine bridge, `kitchen setup-mcp` (W2). The setup agent runs in its tool's sandbox with no network and no Docker, so it cannot run the Toolkit it is writing; the bridge runs one `bin/dev` command, or the whole `toolkit check`, for it, as the engine, outside the agent's sandbox. That is the only way the agent can prove its own Toolkit before the engine commits it, and it is why setup finishes in one pass on fixtures A–D instead of a blind write followed by engine-side fix rounds.

**Risk.** The code the bridge runs was written moments earlier by the agent, from a repo it read: a prompt injection in a README, an issue or a dependency can make the agent write a `bin/dev` that reads the developer's credentials and sends them out. Without confinement, that `bin/dev` runs as the user with network: it can read `~/.ssh`, `~/.aws`, `~/.config/gh`, the agent tools' own auth (`~/.claude`, `~/.codex`) and `$KITCHEN_HOME` (the engine key that signs evidence). The untrusted env (ADR 0006) keeps credentials out of the *environment*, not off the *disk*. App code started by `toolkit check` has the same residual risk (ADR 0006, "an OS sandbox for app processes is a later hardening item"); the bridge is worse only in timing: it runs before a human has reviewed anything.

**Mitigation (macOS).** Every `bin/dev` the bridge runs goes through `/usr/bin/sandbox-exec` with a profile Kitchen writes to `$KITCHEN_HOME/sandbox/setup-bridge.sb` (`src/toolkit/sandbox.ts`): allow by default, then deny every read and write under `~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.config/gcloud`, `~/.azure`, `~/.kube`, `~/.gnupg`, `~/.netrc`, `~/.git-credentials`, `~/.npmrc`, `~/.pypirc`, `~/.claude`, `~/.claude.json`, `~/.codex`, `~/Library/Keychains`, the Claude app's support folder, and `$KITCHEN_HOME`, with `$KITCHEN_HOME/scrub` (the empty git and gh config the untrusted env points at) allowed back for reading. The bridge wraps the path of `bin/dev` (a two-line wrapper in `$KITCHEN_HOME/sandbox/`), so every route it takes is confined: one command, the check's lifecycle calls, the drive interpreter's primitive calls, the contract probe, and a stale slot's reclaim. Children inherit the sandbox. What `bin/dev` needs stays allowed: the repo and the setup worktree, temp, the network, Docker through the guard below and `~/.docker` (CLI config, compose plugin), npm and Playwright caches. Proven by `spikes/w2/sandbox.ts`: a planted `bin/dev` that runs `cat ~/.ssh/*`, reads `~/.config/gh`, `~/.claude`, `~/.codex` and `cat $KITCHEN_HOME/engine.key` gets every read denied through the bridge (each succeeds unsandboxed), and fixture A's Toolkit still passes the full check through the bridge, Docker included.

**Amended by ADR 0015: not on the base and not approved = sandboxed.** The rule below now reads "a sha neither on the base nor approved by the person". One predicate decides it, `trustOf` in `src/toolkit/trust.ts`, and every caller runs its answer (`binFor`): `toolkitCheckout` (jobs, `toolkit check`, `toolkit up`, maintain, the re-proof) and the setup bridge, whose uncommitted worktree is never trusted.

**Not merged = sandboxed (W2 review round 2).** The same code runs again after the bridge: init's own `toolkit check` of the `kitchen/setup` commit, the check after each fix round, and a person's `kitchen toolkit check --rev kitchen/setup` or `toolkit up --rev …`. Until a human merges it, that code is no more trusted than it was in the bridge. So every run of a Toolkit sha that is **not merged**, meaning not an ancestor of the base (the main checkout's `HEAD`, `git merge-base --is-ancestor`), goes through the same profile: `toolkitCheckout` (`src/toolkit/checkout.ts`) hands out the sandbox wrapper as the checkout's `bin` and says so (`merged: false`), and the check prints `is not merged into the base: bin/dev runs under sandbox-exec`. A merged sha (the base, and the base-change re-proof after it moves) runs as before. Proven by `spikes/w2/sandbox.ts`: a planted, working Toolkit that writes a marker whenever it can read `~/.ssh` or `$KITCHEN_HOME/engine.key` leaves no marker through `kitchen init` (survey, build, commit, check: PASS) or `toolkit check --rev kitchen/setup`; after the branch is merged, the same Toolkit's check runs unsandboxed and the marker appears, which is the control.

**Residual.** The deny list is a list: a credential stored somewhere else under `$HOME` (a cloud CLI not named here, `~/.docker/config.json` registry auth, browser profiles) is still readable, and the network is open, so what is readable can leave. The profile denies files, not the macOS keychain service (`security` talks to `securityd`; Docker's credential helper does the same). **The Docker daemon is outside `sandbox-exec`:** the profile confines the processes `bin/dev` starts, but a container is started by the daemon, which runs as its own process (in Docker Desktop's or Colima's VM, with the host folders it shares), so without a guard `docker run -v $HOME:/h …` from a sandboxed `bin/dev` reads `~/.ssh` inside the container, and the sandbox never sees it. A `docker` shim on `PATH` alone would not fix that: a determined `bin/dev` calls the real CLI by path, or `curl --unix-socket` on the daemon's socket. So the boundary is a proxy plus a socket deny (W3b, review M5; `src/toolkit/docker-guard.ts`, `docker-proxy.ts`):

- The sandbox wrapper starts `docker-proxy.ts` **outside** the sandbox on a fresh socket in `/tmp/kitchen-dg.*`, runs `bin/dev` with `DOCKER_HOST` on it (`DOCKER_CONTEXT` and the TLS variables unset), and kills it when `bin/dev` ends. The proxy forwards the Engine API to the daemon socket the engine itself uses (its `DOCKER_HOST` if `unix://`, else `docker context inspect`) and checks **every** request (node's HTTP parser, so each request on a keep-alive connection; exec/attach/BuildKit upgrades become raw streams only after their request line is checked, any other upgrade is refused). It refuses, with a 403 the docker CLI prints as `Error response from daemon: Kitchen (ADR 0008): …`: a container (`containers/create`: `HostConfig.Binds`, bind `Mounts`, the old top-level form, keys in any case as Go reads them) with a bind source that does not resolve (`..` folded, symlinks resolved) into the repo, its `.worktrees/` or temp; `Privileged`; `PidMode`/`NetworkMode`/`IpcMode`/`UsernsMode` `host`; `CapAdd` of `SYS_ADMIN`, `ALL` and the like; `VolumesFrom`; a privileged exec; a local volume that binds a host path outside those roots (`type=none,o=bind,device=…`, in `volumes/create` or inline); swarm services and plugins; a request path that is not canonical. Named volumes, ports, memory limits, `exec -i`, compose and builds pass.
- The profile denies `network-outbound` to the daemon's own sockets: the resolved endpoint and its real path, `/var/run/docker.sock`, `~/.docker/run/docker.sock`, `~/.rd/docker.sock`, everything under `~/.colima`, `~/.lima`, `~/.orbstack` and Docker Desktop's container folder (the sandbox matches the socket's vnode, so links to it are denied too), and denies reading `~/.colima`, `~/.lima` and `~/.orbstack` (their ssh keys open a shell in the daemon's VM).
- The `docker` shim first on `PATH` checks `run`/`create` arguments with the same rules and exits 125 with the reason before anything reaches Docker, and refuses `-H`/`--context`. It is the readable error, not the boundary.
- **Only its own containers** (W5 follow-ups, from the W3b round-2 review). Every request on an existing container (`exec`, `archive` PUT/GET/HEAD, `attach`, `logs`, `kill`, `stop`, `start`, `restart`, `rm`, `update`, `export`, inspect, `commit?container=`) and a network `connect`/`disconnect` goes through only for a container created through the guard. Chosen over requiring the slot's `kitchen.id` label: compose-based Toolkits don't label every container, and a label is something the Toolkit itself writes. The proxy records the id each `containers/create` answers with, one JSON line per container in `$KITCHEN_HOME/sandbox/docker-owned-<repo hash>.jsonl` (per repo, so `up` in one `bin/dev` call and `down` in another, or another checkout of the same repo's Toolkit, share it; the sandbox can't read or write it); for a request it asks the daemon what the name, id or prefix resolves to and lets it through only when that id is recorded. Another project's container (`supabase_db_offstage`) is refused (403), as is one that doesn't exist. `POST /containers/prune` and a build with `networkmode=host` or an insecure entitlement are refused too. Proven by `src/toolkit/docker-proxy.test.ts`: the proxy process against a fake daemon socket (create, exec on its own container, a second proxy removing it; exec, kill and archive on the other project's refused and never forwarded), and the rules in `docker-guard.test.ts`.

Proven by `spikes/w3b/docker-guard.ts`: through the wrapper, `docker run -v $HOME:/h` is refused by the shim, the real CLI by path and a raw `curl` `containers/create` (also with lower-case keys) by the proxy, a `$HOME` bind volume and `compose up` with a `$HOME` bind are refused, `curl` on the Colima socket and `docker -H` on it fail, `--privileged`/`--pid=host`/`--network=host` and `exec --privileged` are refused; binds of the repo, a worktree and temp, named volumes, ports and `docker exec -i` with stdin work, stdout and the exit code are `bin/dev`'s, and a merged `bin/dev` runs unguarded. What remains: a TCP Docker endpoint (`DOCKER_HOST=tcp://…`) is not proxied or denied; containers that already exist are out of reach (above), but a Toolkit's containers created before the guard recorded them can't be stopped by an unmerged `down` (a person removes them once); the daemon still sees every named volume and image (a volume can still be mounted or removed by name); a symlink swapped in between the proxy's check and the daemon's mount is a race the proxy cannot close; a socket path the deny list does not name stays reachable; a merged Toolkit runs unguarded; Linux is unhandled. `sandbox-exec` is deprecated by Apple but still shipped and used (Chromium, Bazel). Once merged, a Toolkit (every job's Toolkit calls, the re-proof) runs unsandboxed: a human has taken it in, and app code has ADR 0006's residual risk.

**Linux: unhandled.** There is no profile on Linux (or on a Mac without `sandbox-exec`); the bridge logs `runs UNSANDBOXED` on start, and a check of an unmerged sha prints `bin/dev runs UNSANDBOXED: no OS sandbox on this platform`. The README states it as a v0.1 limitation. The candidates are bubblewrap or Landlock with the same deny list; that is a later hardening item together with sandboxing app processes.

**Alternatives.** Running the Toolkit only engine-side after the agent ends (no bridge) loses the agent's own prove loop and costs fix rounds. Running it in a container would confine it fully, but a Toolkit's job is to drive the host's Docker and toolchain the way a developer does; that is the W3b+ "Toolkit in a container" question, not a W2 fix.
