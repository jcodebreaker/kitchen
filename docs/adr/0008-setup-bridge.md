# The setup bridge runs agent-written bin/dev, confined by an OS sandbox

**Decision.** `kitchen init`'s setup role gets its own engine bridge, `kitchen setup-mcp` (W2). The setup agent runs in its tool's sandbox with no network and no Docker, so it cannot run the Toolkit it is writing; the bridge runs one `bin/dev` command, or the whole `toolkit check`, for it, as the engine, outside the agent's sandbox. That is the only way the agent can prove its own Toolkit before the engine commits it, and it is why setup finishes in one pass on fixtures A–D instead of a blind write followed by engine-side fix rounds.

**Risk.** The code the bridge runs was written moments earlier by the agent, from a repo it read: a prompt injection in a README, an issue or a dependency can make the agent write a `bin/dev` that reads the developer's credentials and sends them out. Without confinement, that `bin/dev` runs as the user with network: it can read `~/.ssh`, `~/.aws`, `~/.config/gh`, the agent tools' own auth (`~/.claude`, `~/.codex`) and `$KITCHEN_HOME` (the engine key that signs evidence). The untrusted env (ADR 0006) keeps credentials out of the *environment*, not off the *disk*. App code started by `toolkit check` has the same residual risk (ADR 0006, "an OS sandbox for app processes is a later hardening item"); the bridge is worse only in timing: it runs before a human has reviewed anything.

**Mitigation (macOS).** Every `bin/dev` the bridge runs goes through `/usr/bin/sandbox-exec` with a profile Kitchen writes to `$KITCHEN_HOME/sandbox/setup-bridge.sb` (`src/toolkit/sandbox.ts`): allow by default, then deny every read and write under `~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.config/gcloud`, `~/.azure`, `~/.kube`, `~/.gnupg`, `~/.netrc`, `~/.git-credentials`, `~/.npmrc`, `~/.pypirc`, `~/.claude`, `~/.claude.json`, `~/.codex`, `~/Library/Keychains`, the Claude app's support folder, and `$KITCHEN_HOME`, with `$KITCHEN_HOME/scrub` (the empty git and gh config the untrusted env points at) allowed back for reading. The bridge wraps the path of `bin/dev` (a two-line wrapper in `$KITCHEN_HOME/sandbox/`), so every route it takes is confined: one command, the check's lifecycle calls, the drive interpreter's primitive calls, the contract probe, and a stale slot's reclaim. Children inherit the sandbox. What `bin/dev` needs stays allowed: the repo and the setup worktree, temp, the network, the Docker socket and `~/.docker` (contexts, compose plugin), npm and Playwright caches. Proven by `spikes/w2/sandbox.ts`: a planted `bin/dev` that runs `cat ~/.ssh/*`, reads `~/.config/gh`, `~/.claude`, `~/.codex` and `cat $KITCHEN_HOME/engine.key` gets every read denied through the bridge (each succeeds unsandboxed), and fixture A's Toolkit still passes the full check through the bridge, Docker included.

**Not merged = sandboxed (W2 review round 2).** The same code runs again after the bridge: init's own `toolkit check` of the `kitchen/setup` commit, the check after each fix round, and a person's `kitchen toolkit check --rev kitchen/setup` or `toolkit up --rev …`. Until a human merges it, that code is no more trusted than it was in the bridge. So every run of a Toolkit sha that is **not merged**, meaning not an ancestor of the base (the main checkout's `HEAD`, `git merge-base --is-ancestor`), goes through the same profile: `toolkitCheckout` (`src/toolkit/checkout.ts`) hands out the sandbox wrapper as the checkout's `bin` and says so (`merged: false`), and the check prints `is not merged into the base: bin/dev runs under sandbox-exec`. A merged sha (the base, and the base-change re-proof after it moves) runs as before. Proven by `spikes/w2/sandbox.ts`: a planted, working Toolkit that writes a marker whenever it can read `~/.ssh` or `$KITCHEN_HOME/engine.key` leaves no marker through `kitchen init` (survey, build, commit, check: PASS) or `toolkit check --rev kitchen/setup`; after the branch is merged, the same Toolkit's check runs unsandboxed and the marker appears, which is the control.

**Residual.** The deny list is a list: a credential stored somewhere else under `$HOME` (a cloud CLI not named here, `~/.docker/config.json` registry auth, browser profiles) is still readable, and the network is open, so what is readable can leave. The profile denies files, not the macOS keychain service (`security` talks to `securityd`; Docker's credential helper does the same). **The Docker daemon is outside `sandbox-exec`:** the profile confines the processes `bin/dev` starts, but a container is started by the daemon, which runs as its own process (in Docker Desktop's VM, with the host folders it shares), so `docker run -v $HOME:/h …` from a sandboxed `bin/dev` reads `~/.ssh` inside the container, and the sandbox never sees it. Planned for W3b+, not built: the engine refuses (or rewrites) bind mounts outside the repo, its worktrees and temp for any Toolkit run, by checking `docker run`/compose arguments through a Docker shim or an authorization plugin. `sandbox-exec` is deprecated by Apple but still shipped and used (Chromium, Bazel). Once merged, a Toolkit (every job's Toolkit calls, the re-proof) runs unsandboxed: a human has taken it in, and app code has ADR 0006's residual risk.

**Linux: unhandled.** There is no profile on Linux (or on a Mac without `sandbox-exec`); the bridge logs `runs UNSANDBOXED` on start, and a check of an unmerged sha prints `bin/dev runs UNSANDBOXED: no OS sandbox on this platform`. The README states it as a v0.1 limitation. The candidates are bubblewrap or Landlock with the same deny list; that is a later hardening item together with sandboxing app processes.

**Alternatives.** Running the Toolkit only engine-side after the agent ends (no bridge) loses the agent's own prove loop and costs fix rounds. Running it in a container would confine it fully, but a Toolkit's job is to drive the host's Docker and toolchain the way a developer does; that is the W3b+ "Toolkit in a container" question, not a W2 fix.
