devkitchen · architecture · v0 proposal

Kitchen

An open-source pipeline that takes a ticket and hands you a pull request that has been proven by driving your real app, not just read. Agents (Claude Code or Codex) make the judgment calls. A TypeScript CLI owns every state change, check and retry. Your project's Toolkit is the only way anything touches the running app.

What a job goes through

Stages and their contracts

Every agent reads files, writes exactly one file, and answers with one line. A script reads that line and moves the job, or refuses with a reason. The kitchen names are optional flavour for the docs.

StageWhoWritesMoves on when
Intakethe orderagent · strongACCEPT, NEEDS-INFO or REJECT. Kind (feature, bug, chore), risk, surfaces. A smaller scope if the ticket is too big.Script reads the header. Every part cut from scope is filed as a new ticket, so nothing is dropped.
Specmise en placeagentA short verification contract, not a long document: each acceptance criterion names how it will be proven (a Toolkit drive, a command, or a test). The builder may only tick criteria off, never edit them.spec-lint passes: no criterion needs a protected file, and every drive the spec names exists in the Toolkit. A missing drive becomes a Toolkit gap now, before any code is written. For bugs, Verify reproduces the bug first.
Buildthe lineagent · strongCommits on its own branch and worktree, a draft PR, build notes. May self-check with its own Toolkit instance.Tree clean, branch pushed, PR open. The builder's own evidence is a hint, never the proof.
Gatetemp checkscriptGate report pinned to the commit.Your checks pass from main's copy of the config, and no protected path changed.
Verifytaste testagent · freshOne Verdict per criterion, with screenshots, logs and side effects in evidence/.PASS on every criterion. FAIL goes back to Build. TOOLKIT-GAP pauses the job for the Toolkit smith. INCONCLUSIVE counts as FAIL.
Reviewchef's eyeagents · routedOne file per lens: code always, security, UX and UI when intake flags the surface.No blocking finding. A finding blocks only if the reviewer can show it (a failing run, a wrong line). Findings are de-duplicated and confidence-filtered, and each lens's precision is tracked in the ledger; a lens or category that keeps being dismissed is muted.
Readythe passscript + 1 verifierReady report on the PR, evidence linked.Synced with main, then Gate and a single Verify pass again on the synced head. The PR is marked ready.
Reportthe billagent · mediumAn HTML page: what was done, each criterion with its Verdict, the tests that ran, screenshots and logs. Proof is cited only by evidence id.The CLI swaps each id for the real file and refuses an id that doesn't exist, so made-up proof can't be saved. Linked from the PR and the dashboard.
MergeserviceyouYou merge. Auto-merge for low-risk tickets with no UI or security surface is an opt-in setting, off by default.
Not every ticket gets every stage

Risk sets the path

RiskPathA human
lowsmall chore, no UI, no securityIntake writes the criteria inline, so there is no separate Spec. Build, Gate, one short Verify drive, a code review only above a diff-size limit, then Ready and Report.Merges. Auto-merge is possible if the project opts in.
mediumEvery stage.Merges.
highdata, money, auth, migrationsEvery stage, plus the security lens. Verify drives every related feature in the feature map.Always reviews the diff, the Verdicts and the Report before merging.

Rules for the whole pipeline: agents check other agents only at Verify and Review, and everything else is checked by structure or scripts. Cost is shown per job and never stops one.

Closed laptop, lost session

Picking a job back up

Everything a job needs is stored as files in the repo: its stage, round, worktree, evidence, and each agent run's session id. The CLI keeps a lock with its process id and a heartbeat, so it can tell a dead run from a live one. Next day, kitchen run (or /kitchen) cleans up stale Toolkit instances, runs doctor and up again, and continues every job from its stage. A step that was cut off re-runs from its start with a fresh agent that gets the earlier files. Every step is safe to run twice. kitchen status lists each job as number and slug (012-dark-mode-toggle), title, stage and when it last moved. kitchen resume 012 picks one.

Why these choices

What the evidence says

Most production numbers are reported by the vendors themselves. Academic studies are marked as such.

ChoiceStrengthWhat it rests on
A verifier that never wrote the codestrongModels don't reliably fix their own mistakes without outside feedback (Huang et al., ICLR 2024). In METR's samples, maintainers would not merge many PRs that had passed the tests. Anthropic's harness (Mar 2026) uses a separate evaluator that drives the app with Playwright, because agents "confidently praise" their own work.
Bugs reproduce firststrongGoogle Passerine fixed about 30% more bugs when given reproduction tests. In SWT-bench (NeurIPS 2024), checking patches against generated failing tests roughly doubled precision.
Review that cuts noisemediumUber, Cursor Bugbot and Google Tricorder all lean on confidence filters, de-duplication and muting categories that developers dismiss. Bugbot replaced 8 voting passes with one exploring agent.
Rules promoted or pruned by feedbackmediumBugbot's learned rules (Apr 2026) come from dismissals and from bugs it missed. Vendor-reported.
Risk scores for gatingmediumMeta's Diff Risk Score (2025): 42% more changes landed and 52% fewer outages during code freezes. There's no evidence for using risk to pick the review model.
Long specs before buildingweakAn ESEM 2026 study found spec documents did not reduce defects. The part that seems to help is agreeing how success will be checked, so Kitchen's Spec stays a short verification contract.
Several builds per ticket plus a judgedeferredGains on benchmarks only with a trained critic or tests to pick the winner. No production data on cost per merged PR.
Rounds, escalation reasons, revert rate, cost per merged PRnew groundNo public system was found that publishes these. Kitchen's ledger measures them, and counts merge rate as merged PRs out of tickets taken in, not out of PRs opened.
Decisions

Settled, and what I need from you

Q1
Open source, for every developer. Setup must be easy from Claude Code or Codex.
Q2–3
Setup adopts or builds the dev environment, then builds the Toolkit. The Toolkit is the one contract every stage uses.
Q4–6
The Toolkit keeps growing. Jobs extend it for new features. A Toolkit gap pauses the job while a separate smith builds the tool on its own branch, proven on main, at most two tries.
Q7–9
A TypeScript CLI owns the loop, run with npx, with Claude Code and Codex as adapters. The Toolkit can be any language. It must provide up, doctor and down with an id and JSON output.
Q10–12
Tickets come from GitHub issues or a prompt. The product is Kitchen, the repo is pttx/kitchen, the npm package is devkitchen.
Q13
You merge by default. Auto-merge for low-risk tickets is opt-in.
Q14
The stages above, accepted for now: Spec as a short verification contract, spec-lint before building, Verify as its own stage, and bugs reproduced first. Kept under watch in case it proves too heavy.
Q15
Risk sets the path: low risk takes the short path, high adds security and a human. It doesn't pick which model reviews.
Q16
Report stage. A medium-model agent writes the HTML, citing proof only by evidence id, and the CLI fills in the real files. Agents check other agents only at Verify and Review.
Q17
Resume from files, using a lock plus heartbeat. Jobs are named by number and slug, with the title shown.
Q18
Retro mutes noisy review categories by itself and files bigger lessons as tickets you approve. Kitchen never rewrites its own rules.
Q19
Left out of v1: competing builds, cloud runners, GitLab and Linear, and Windows.
Q20
Defaults: two jobs at once. The strongest model for intake and build, a medium model for verify, review and report, a cheap one for retro. Ticket text is data, never instructions. Secrets stay out of the Toolkit. No cost cap. Cost is shown, never enforced.
